# Designing hat collections

Checks for a new or revised hat collection. Each one comes from a failure measured in real runs. Apply all of them to every hat.

1. **Every published topic has a subscriber.** A topic no hat triggers on falls through to Ralph's coordinator, which spends a full iteration translating it. For example, a reviewer publishing `review.revision` while the writer triggers on `edit.revision`. `ralph hats validate` warns about each one ("published by … has no hat subscribers").
2. **Each hat names every path it reads.** A hat sees only its own instructions, never another hat's. So "the shared docs directory" with no path leaves it guessing.
3. **One event per hat iteration.** A hat with several possible outcomes publishes exactly one of them, chosen by stated conditions.
4. **No per-item bookkeeping hats.** Each fresh iteration pays a fixed prompt cost, about $0.21 per iteration on Claude in one measurement. A hat that only picks the next item, or only closes an item and advances a queue, pays that on every item. In one implementation loop those hats were 41% of spend. Fold that work into the neighboring hat. For example, a reviewer that passes a task closes it and hands the next ready task straight to the builder.
5. **Re-plan on signal, not on a schedule.** When later work depends on what earlier slices teach, let the reviewer or builder publish a revise event (for example `plan.revise`) that sends the planner back to revise only the remaining work. Don't route through the planner after every item.
6. **Size work for the review cycle.** Each item costs a build-and-review round trip, so make each one the largest increment a reviewer can still check in one pass.
7. **Reviewers carry a severity rule.** An unconstrained adversarial reviewer always finds something. In one run a single task was rejected four times, the last two for minor findings only. Reject for blocking findings: wrong behavior on realistic input, a check that passes when it should fail, data loss, failing verification, or a missed requirement. Pass with minor findings logged as follow-ups. Before rejecting again, confirm that the earlier findings were fixed.
8. **State goals in plain language.** Give the role, inputs, what to publish, what done means, and how to verify it. Current models follow instructions closely and literally, so all-caps MUST/NEVER and step-by-step scripts for judgment work over-apply. Keep exact steps only where order truly matters.
9. **Fit model and effort to the role.** Set them per hat with `model` and `effort` (see `schema.md`). A planner that runs rarely can afford the most capable model. Builders and reviewers set the quality of the loop. Gating and bookkeeping work runs fine at lower effort. A reviewer from a different model family than the builder is less likely to share its blind spots.
