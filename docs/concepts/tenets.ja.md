# 6 つの信条

Ralph の設計は、6 つの中核となる信条に導かれています。これらを理解すると、Ralph と
効果的に協働できます。

## 1. フレッシュコンテキストは信頼性

> 各イテレーションはコンテキストをクリアする。毎サイクル、スペック、計画、コードを読み直す。

**意味するところ:**

各イテレーションはまっさらから始まります。AI は以前のイテレーションの状態をコンテキスト
ウィンドウに持ち越さず、すべてを読み直します。

**なぜ重要か:**

- 混乱の蓄積を防ぐ
- 各イテレーションが成功のための新たな機会になる
- 失敗した試行による「汚染された」コンテキストがない
- 「スマートゾーン」（使用可能トークンの 40〜60%）に最適化される

**どう適用するか:**

- AI が以前のイテレーションを覚えていることに頼らない
- 会話履歴ではなく、永続的な状態にファイルを使う
- プロンプトを自己完結させる

## 2. 規定よりバックプレッシャー

> どうやるかを規定しない。悪い作業を拒否するゲートを作る。

**意味するところ:**

Ralph に何かのやり方を正確に指示する代わりに、不完全な作業をブロックする品質ゲートを
定義します。

**なぜ重要か:**

- AI エージェントは賢い。「どうやるか」は自分で考えられる
- 規定は脆く、バックプレッシャーは堅牢
- テスト、lint、型チェックは普遍的な品質の尺度

**どう適用するか:**

```yaml
# 手順を規定しない
instructions: |
  1. First, create the file
  2. Then, add the function
  3. Then, write tests

# バックプレッシャーを使う
instructions: |
  Implement the feature.
  Evidence required: tests: pass, lint: pass, typecheck: pass, audit: pass, coverage: pass
```

## 3. 計画は使い捨て

> 再生成のコストは計画ループ 1 回分。安い。

**意味するところ:**

計画は再生成が安いものです。失敗している計画を守ろうと戦わないでください。新しく作れば
よいのです。

**なぜ重要か:**

- 計画は速く、実装は遅い
- 新しい計画はサンクコストの誤謬を避ける
- 壊れたアプローチにパッチを当てるより、やり直したほうがよい

**どう適用するか:**

- Ralph に計画を自由に再生成させる
- 複雑な「計画修復」ロジックを追加しない
- うまくいかないなら、新しい計画は 1 イテレーション先にある

## 4. ディスクは状態、Git は記憶

> ファイルが引き継ぎの仕組みである。

**意味するところ:**

すべての永続的な状態はディスク上にあります。

- `.ralph/agent/memories.md` — 蓄積された知恵
- `.ralph/agent/tasks.jsonl` — ランタイムの作業追跡
- コードベースそのもの
- Git 履歴

**なぜ重要か:**

- 単純で、信頼でき、デバッグしやすい
- 複雑な調整の仕組みが不要
- Git が無料でバージョン管理と履歴を提供する

**どう適用するか:**

- セッションをまたいだ学習にメモリファイルを使う
- ランタイムの追跡にタスクを使う
- 重要なチェックポイントを git にコミットする

## 5. スクリプトではなく信号で舵を取る

> 次回のために標識を加える。始めたときのプロンプトが、終わるときのプロンプトになるとは
> 限らない。

**意味するところ:**

Ralph が特定の形で失敗したら、次回それを防ぐための信号（テスト、lint ルール、ガードレール）
を加えます。正確な挙動をスクリプト化しようとしないでください。

**なぜ重要か:**

- スクリプトは硬直的、信号は適応的
- コードベースが指示書になる
- Ralph は自らの環境から学ぶ

**どう適用するか:**

```yaml
# 信号: ガードレールを加える
guardrails:
  - "Always run tests before declaring done"
  - "Never modify production database directly"

# 正確な手順をスクリプト化しない
# （これはやらない）
```

## 6. Ralph に Ralph させる

> ループの*中*ではなく、ループの*上*に座る。オーケストラを指揮するのではなく、ギターを
> チューニングするように。

**意味するところ:**

あなたの仕事は、環境と制約を整えてから Ralph に任せることです。各イテレーションを細かく
管理しないでください。

**なぜ重要か:**

- Ralph は設計上、自律的である
- 介入はイテレーションのサイクルを乱す
- そもそもの狙いは手を離した運用である

**どう適用するか:**

- 上限を設定する（イテレーション、費用、時間）
- バックプレッシャーゲートを設定する
- TUI で監視する
- 必要なときだけ介入する

## アンチパターン

次のパターンは信条に反します。

| アンチパターン | なぜ悪いか | 違反する信条 |
|--------------|--------------|----------------|
| 機能をオーケストレーターに組み込む | エージェントが処理できる | #6 Ralph に Ralph させる |
| 複雑なリトライロジック | フレッシュコンテキストが復旧を担う | #1 フレッシュコンテキスト |
| 詳細な逐次手順の指示 | 代わりにバックプレッシャーを使う | #2 バックプレッシャー |
| タスク選択時に作業のスコープを決める | 計画作成時にスコープを決める | #3 計画は使い捨て |
| 機能が存在しないと仮定する | まず検索する | （全般） |

## 要約

| 信条 | 中核の考え |
|-------|-----------|
| 1. フレッシュコンテキスト | 各イテレーションはまっさらから始まる |
| 2. バックプレッシャー | スクリプトではなくゲート |
| 3. 使い捨ての計画 | 自由に再生成する |
| 4. ディスクは状態 | ファイルが真実 |
| 5. スクリプトではなく信号 | 手順ではなく標識を加える |
| 6. Ralph に Ralph させる | 手を離す |
