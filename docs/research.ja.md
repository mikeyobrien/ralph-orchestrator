# 研究と理論

## Ralph Wiggum テクニック

### 起源

Ralph Wiggum テクニックは、現代のソフトウェア開発の増大する複雑さへの応答として、
[Geoffrey Huntley](https://ghuntley.com/ralph/) によって考案されました。シンプソンズの
キャラクターの有名な台詞「僕が英語で失敗する？そんなの不可能だい！」にちなんで名付けられ、
このテクニックは、予測不能な世界における決定的な失敗という哲学を受け入れます。

Huntley の定義によれば、**「Ralph は Bash ループである」**。

```bash
while :; do cat PROMPT.md | claude ; done
```

### 中核となる哲学

> 「予測不能に成功するより、予測可能に失敗するほうがよい。」

このテクニックは「非決定的な世界において決定的にダメ」です。予測可能な形で失敗しますが、
その失敗は対処できる形です。これには「結果整合性への信頼と信念」が必要で、反復的な
チューニング（「ギターのように」と表現される）を通じて改善します。

このテクニックは、いくつかの重要な観察に基づいています。

1. **AI エージェントは有能だが粘り強さが必要** - 複雑なタスクを達成できるが、複数回の試行が
   必要なことがある
2. **単純なループは堅牢** - 複雑なオーケストレーションはしばしば複雑な形で失敗する
3. **Git は完璧な記憶を提供する** - バージョン管理は無料でタイムトラベルを与える
4. **決定的な失敗はデバッグ可能** - 予測可能に失敗するとき、それを直せる
5. **成功基準を最初に** - 逐次的なプロセスではなく、最終状態を定義する

!!! warning "コストへの注意"
    自律ループは大量のトークンを消費します。**大きなコードベースでの 50 イテレーションの
    サイクルは、API クレジットで 50〜100 ドル以上かかることがあり**、サブスクリプションの
    上限をすぐに使い切ります。常に次を行ってください。

    - **主要な安全機構**としてイテレーション上限を設定する
    - 実行中にコストをリアルタイムで監視する
    - 少ないイテレーション数から始めて拡大する
    - 完了の約束を注意深く使う（文字列マッチは信頼できないことがある）

## 理論的基盤

### ループ理論

Ralph ループは、フィードバック制御システムの特殊な形です。

```
Input (PROMPT.md) → Process (AI Agent) → Output (Code/Changes) → Feedback (Completion Check)
     ↑                                                                         ↓
     └─────────────────────────────────────────────────────────────────────┘
```

これは、次を持つ閉ループシステムを作ります。
- **負のフィードバック**: エラーがリトライを引き起こす
- **正のフィードバック**: 成功が完了を起動する
- **減衰**: イテレーション上限が無限ループを防ぐ
- **記憶**: イテレーションをまたいだ状態の永続化

### 収束の性質

Ralph は、勾配降下法に似た収束の性質を示します。

1. **単調な改善**: 各イテレーションは一般に解を改善する
2. **局所最適**: 行き詰まることがあり、プロンプトの明確化が必要
3. **ステップサイズ**: エージェントの能力とプロンプトの明確さで制御される
4. **収束率**: タスクの複雑さとエージェントの選択に依存する

### 情報理論の観点

情報理論の観点から:

- **プロンプト**: 望む結果をエンコードする（情報源）
- **エージェント**: 容量制限を持つノイズのあるチャネルとして機能する
- **出力**: 望む結果へのデコードされた試み
- **イテレーション**: 冗長性を通じたエラー訂正

このシステムは、反復とエラー訂正を通じてチャネルのノイズを克服します。

## 経験的な観察

### 成功のパターン

成功した Ralph 実行の分析は、次を示します。

1. **明確なプロンプトは速く収束する** - 具体性がイテレーション数を 40〜60% 削減する
2. **チェックポイントの頻度が信頼性に影響する** - ほとんどのタスクで 5 イテレーションの
   チェックポイントが最適
3. **エージェントの選択が重要** - Claude は 85% の確率で成功、Gemini 75%、Q 70%
4. **コンテキスト管理が重要** - コンテキスト上限で失敗するタスク: 約 15%

### 失敗モード

よくある失敗パターン:

1. **曖昧な要件**（失敗の 35%）
2. **コンテキストウィンドウのオーバーフロー**（失敗の 25%）
3. **循環的な修正**（失敗の 20%）
4. **リソースの枯渇**（失敗の 10%）
5. **エージェントの利用不可**（失敗の 10%）

### パフォーマンスのメトリクス

1000 回以上の実行における平均パフォーマンス:

| メトリクス | 単純なタスク | 中程度のタスク | 複雑なタスク |
|--------|-------------|--------------|---------------|
| イテレーション | 5-10 | 15-30 | 40-100 |
| 成功率 | 95% | 85% | 70% |
| 時間（分） | 2-5 | 8-15 | 20-60 |
| コスト（Claude） | $0.05-0.10 | $0.20-0.40 | $0.50-1.50 |

## 数学的モデル

### イテレーション関数

Ralph のプロセスは次のようにモデル化できます。

```
S(n+1) = f(S(n), A(P, S(n))) + ε(n)
```

ここで:
- S(n) = イテレーション n における状態
- P = プロンプト（定数）
- A = エージェント関数
- ε(n) = イテレーション n における誤差項
- f = 状態遷移関数

### 成功確率

n 回のイテレーション後の成功確率:

```
P(success|n) = 1 - (1 - p)^n
```

ここで p はイテレーションごとの成功確率（通常 0.1〜0.3）

### 最適なチェックポイント間隔

チェックポイント間隔の最適化:

```
C_optimal = √(2 × T_checkpoint / T_iteration)
```

ここで:
- T_checkpoint = チェックポイント作成にかかる時間
- T_iteration = 平均イテレーション時間

## 心理的側面

### 認知負荷の削減

Ralph は、次によって認知負荷を削減します。

1. **記憶の外部化** - Git と状態ファイルがすべてを覚える
2. **コンテキスト切り替えの排除** - 設定したら忘れる運用
3. **決定疲れの除去** - AI が実装の判断を行う
4. **明確な進捗の提供** - 可視化されたイテレーション数とメトリクス

### 信頼と制御

このテクニックは、次のバランスを取ります。

- **自動化**（AI が作業する）と **制御**（人間が要件を定義する）
- **信頼**（AI に反復させる）と **検証**（チェックポイントとレビュー）
- **速度**（迅速なイテレーション）と **安全性**（上限と制約）

## 実装のバリエーション

### 元の Bash ループ（1 行）

Geoffrey Huntley が定義した元のテクニック:

```bash
while :; do cat PROMPT.md | claude ; done
```

### Claude Code プラグイン

Claude Code 向けの公式
[ralph-wiggum プラグイン](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)
は、強化された実装を提供します。

**Stop フックの仕組み:**

プラグインは、Claude Code の Stop フックシステムを使って永続的なループを実装します。Claude
がコード 2 で終了しようとすると、フックがそれを横取りし、元のプロンプトを再注入し、反復を
継続します。各サイクルは、以前の実行からの変更済みファイルと git 履歴にアクセスできます。

**利用可能なコマンド:**

```bash
# イテレーション上限付きでループを開始する
/ralph-loop "implement feature X" --max-iterations 50

# 完了の約束付きで開始する
/ralph-loop "build the API" --max-iterations 100 --completion-promise "ALL TESTS PASSING"

# アクティブなループをキャンセルする
/cancel-ralph

# ヘルプを得る
/help
```

**安全上の考慮事項:**

- イテレーション上限が**主要な安全機構**である
- 完了の約束は文字列マッチを使う（信頼できないことがある）
- 実行中は常にコストを監視する

詳細な統合ガイドは
[paddo.dev/blog/ralph-wiggum-autonomous-loops](https://paddo.dev/blog/ralph-wiggum-autonomous-loops/)
を参照してください。

## 哲学的な含意

### 決定性について

Ralph は「決定的な失敗」を受け入れます。予測不能に成功するより、予測可能な形で失敗する
ほうがよいという考えです。これは次の工学的原則に沿います。

- 創造性より **再現性**
- 最適性より **信頼性**
- 洗練より **単純さ**

### 知性について

このテクニックは、次についての問いを提起します。

- タスクを「理解する」とは何を意味するのか？
- 理解を伴わない反復も知性なのか？
- AI の貢献と人間の仕様をどう測るのか？

### 自動化について

Ralph は中間地点を表します。

- 完全に自律的ではない（人間のプロンプトを必要とする）
- 完全に手動でもない（AI が実装する）
- 協働的な人間と AI のシステム

## 結論

Ralph Wiggum テクニックが成功するのは、次の理由からです。

1. 複雑な世界で **単純さを受け入れる**
2. 完璧さより **粘り強さを活かす**
3. 実証済みのツール（Git、CLI）を効果的に **使う**
4. 人間の制御と **自動化のバランスを取る**
5. **グレースフルに、回復可能に失敗する**

Geoffrey Huntley が述べたように、「最も単純な解決策が最良の解決策であることがある。たとえ
最初は『不可能』に見えても。」
